# Задача: вынести обработку видео из HTTP-запроса в отдельный Worker

Необходимо переработать существующую архитектуру загрузки и обработки видео в проекте YourTube.

**Главная цель:** HTTP-запрос должен отвечать только за получение и сохранение исходного файла. Перекодирование через FFmpeg, генерация обложки и публикация должны выполняться асинхронно отдельным Worker.

## 1. Новая архитектура

Реализовать следующую последовательность:

1. Пользователь загружает видео через существующий интерфейс.
2. FastAPI проверяет авторизацию, валидирует данные и сохраняет исходный файл.
3. В PostgreSQL создаётся запись видео со статусом `queued`.
4. Сервер возвращает HTTP `202 Accepted` с идентификатором видео, не ожидая выполнения FFmpeg.
5. Отдельный Worker получает задание из PostgreSQL.
6. Worker переводит видео в статус `processing`, запускает FFmpeg и генерирует обложку.
7. После успешной обработки статус меняется на `ready`, видео становится доступным для просмотра.
8. При ошибке статус меняется на `failed`, причина сохраняется в PostgreSQL.

## 2. Очередь заданий

Использовать PostgreSQL как постоянное хранилище очереди. Не добавлять Redis, RabbitMQ или Celery без необходимости.

Требования:

- Задания должны переживать перезапуск контейнеров.
- Несколько Worker не должны одновременно обрабатывать одно видео.
- Для получения заданий использовать безопасную конкурентную блокировку, например `FOR UPDATE SKIP LOCKED`.
- Одновременно обрабатывать максимум два видео.
- После аварийного завершения Worker незавершённое задание должно быть обнаружено и повторно поставлено в очередь.
- Реализовать ограничение количества повторных попыток.
- Предусмотреть защиту от повторной публикации и повреждения уже обработанных файлов.

Использовать механизм аренды заданий (lease) с временем истечения и периодическим продлением, чтобы обнаруживать зависшие обработки.

## 3. Отдельный Docker-контейнер

Добавить сервис `worker` в существующий `compose.yaml`.

Worker должен:

- Использовать существующий образ приложения, если это возможно.
- Иметь доступ к PostgreSQL и общему файловому хранилищу видео.
- Запускаться автоматически через Docker Compose.
- Перезапускаться после сбоев.
- Корректно завершать текущие операции при штатной остановке.
- Не зависеть от открытых HTTP-соединений пользователей.

Не создавать дополнительных Compose-файлов. Сохранить существующую структуру проекта и механизм развёртывания.

## 4. Отображение прогресса

Добавить API для получения состояния обработки видео.

Пример ответа:

```json
{
  "video_id": 123,
  "status": "processing",
  "progress": 47,
  "error": null
}
```

Прогресс должен отражать реальное выполнение FFmpeg, а не имитироваться таймером.

В интерфейсе отображать отдельно:

- Прогресс загрузки исходного файла.
- Ожидание в очереди.
- Прогресс обработки видео.
- Успешную публикацию.
- Ошибку обработки с понятным сообщением.

Для обновления прогресса достаточно периодического опроса API. WebSocket необязателен.

## 5. Управление файлами и ошибками

- Исходные файлы должны сохраняться в общем постоянном хранилище, доступном Worker.
- Не использовать временные каталоги, которые исчезают при завершении HTTP-запроса.
- Не публиковать видео до завершения перекодирования.
- Результаты обработки сначала записывать во временные файлы, затем атомарно перемещать в окончательные.
- При ошибке очищать ненужные промежуточные файлы.
- Предусмотреть удаление устаревших и осиротевших файлов.
- Сохранять существующие ограничения размера и продолжительности видео.
- Реализовать безопасное удаление видео, находящегося в очереди или в процессе обработки.
- Исключить ситуацию, когда удалённое пользователем видео повторно появляется после завершения Worker.
- Ограничить общий расход дискового пространства.

## 6. Совместимость

Сохранить существующую функциональность YourTube:

- Авторизацию и регистрацию.
- Приватность видео.
- Выдачу и отзыв доступа.
- Модерацию.
- Просмотры.
- Редактирование метаданных.
- Удаление видео.
- Существующий веб-интерфейс.

Не переписывать проект с нуля. Изменять только необходимые компоненты и связанные с ними зависимости.

## 7. Тестирование

Добавить автоматические тесты, проверяющие:

1. HTTP-запрос завершается после сохранения файла, не дожидаясь FFmpeg.
2. Видео правильно проходит состояния `queued → processing → ready`.
3. Ошибка FFmpeg приводит к состоянию `failed`.
4. Одно задание не обрабатывается одновременно несколькими Worker.
5. Перезапуск Worker не приводит к потере задания.
6. Удаление видео во время обработки не приводит к его повторной публикации.
7. Видео со статусом `queued`, `processing` или `failed` недоступно для воспроизведения.
8. Приватность сохраняется на всех этапах обработки.

## 8. Критерии готовности

Результат считать завершённым только тогда, когда:

- FFmpeg больше не запускается непосредственно из HTTP-обработчика.
- Загрузка завершается HTTP `202` после надёжного сохранения исходника и постановки задания в очередь.
- Worker работает как отдельный контейнер.
- Очередь сохраняется при перезапуске приложения.
- Интерфейс показывает реальный прогресс.
- Ошибки обработки не нарушают целостность БД и файлов.
- Существующие функции продолжают работать.
- Новые и существующие тесты проходят успешно.

**Важно:** не использовать `FastAPI BackgroundTasks` как замену полноценной очереди, поскольку задания должны сохраняться и восстанавливаться при перезапуске процесса. Не делать вид, что асинхронность реализована, если FFmpeg по-прежнему выполняется в рамках жизненного цикла HTTP-запроса.
